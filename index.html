Overview — What Happens When Someone Asks a Question

When someone asks a Copilot Studio agent a question, the agent does not simply generate an answer from its general knowledge. It first searches for relevant information from the configured knowledge sources, then uses that information to write a grounded response.

This search-then-answer approach is called Retrieval Augmented Generation (RAG). The quality of the answer depends directly on the quality of the retrieval. Same AI model, same question — better retrieval means a better answer.

Think of it this way Two people take the same exam. One is given three pages of notes. The other is given seven pages covering more topics. The person with more relevant notes writes a better answer — not because they are smarter, but because they had better material to work with. The AI works the same way.

Two Indexes — The Key Concept

SharePoint has two different indexes. Understanding the difference is essential.

The SharePoint Search Index (The Original)

This has existed for years. It is a catalogue of every word in every file in SharePoint. When you use the SharePoint search bar, this is what you are searching. It matches words — if you search for "safety valve", it finds files containing those exact words. If a document says "pressure relief mechanism" instead, it will not find it.

The Semantic Index (The AI Layer)

This is a separate, newer layer built on top of the SharePoint search index. It was created for AI and Copilot scenarios.

It takes everything from the SharePoint search index and adds understanding of meaning. It converts content into vectors — numerical representations where similar concepts are grouped together. This means "safety valve", "pressure relief valve", and "overpressure protection" are all understood as related.

AspectSharePoint Search IndexSemantic Index
Available sinceYears agoBuilt for the Copilot era
How it searchesKeyword matching onlyKeywords AND meaning
Admin setupSome controls availableFully automatic — cannot be disabled
Built bySharePointA separate Microsoft 365 service
Who owns itSharePointNot Copilot Studio — Studio is a consumer of this index

How They Relate

The Semantic Index depends on the SharePoint search index. If a file is not in the SharePoint search index (for example, search is disabled for that site), it will not be in the Semantic Index either, and the agent will not find it.

One-sentence version The SharePoint search index knows what words are in your files. The Semantic Index understands what your files mean. Copilot Studio with Tenant Graph Grounding uses the Semantic Index.

Tenant Graph Grounding with Semantic Search

Tenant Graph Grounding is a setting in Copilot Studio (Settings → Generative AI) that controls which search pipeline your agent uses when querying SharePoint content.

AspectGraph Grounding OFFGraph Grounding ON
Search methodBasic SharePoint search (keywords)Full Semantic Index (keywords + meaning + Graph signals)
Maximum file size15 MB200 MB
ResultsFewer, keyword-matched"Greater volume of context, with greater precision"
Graph signalsNoYes — metadata, activity, people signals

Requirements

  • Generative orchestration must be turned on
  • Agent authentication must be set to Authenticate with Microsoft
  • At least one Microsoft 365 Copilot licence must be assigned to a user in the tenant
  • The agent maker does not need a Microsoft 365 Copilot licence
  • Extra cost: Copilot Credits apply for users without Microsoft 365 Copilot licences
  • May introduce slightly higher latency
Simple explanation Tenant Graph Grounding is the upgrade switch for SharePoint retrieval. It connects your agent to the Semantic Index instead of basic SharePoint search. It is not a separate feature — it is the difference between standard and premium retrieval.

The Retrieval Pipeline — Step by Step

When a user asks a question and Tenant Graph Grounding is enabled, the following steps occur. This is specific to the SharePoint knowledge source path.

1

Query Rewriting

Before searching, Copilot Studio rewrites the user's question to improve retrieval quality:

  • Clarifies meaning — resolves vague references using conversation context
  • Adds context from the last 10 messages — if the user says "what about that one?", the system uses recent messages to determine what "that one" refers to
  • Strips filler words and extracts key terms
  • Generates parallel queries — a keyword version (exact terms) and a semantic version (meaning-based), both run simultaneously
▼
2

Content Retrieval

The rewritten queries search the pre-built Semantic Index — not the actual SharePoint files. Two types of search run in parallel:

Search TypeHow It WorksGood For
Lexical (BM25)Traditional word matching against indexed contentPart numbers, product codes, exact names
Semantic (Vector)Meaning-based matching using vector similarityFinding related concepts without exact words

Results from both searches are combined using Reciprocal Rank Fusion — content that scores well in both searches ranks highest.

Graph Signals (Additional Ranking)

On top of hybrid search, Microsoft Graph provides additional ranking signals:

SignalWhat It DoesImportance
Hybrid search scoreHow well content matches the query (keywords + meaning)Primary — the main driver
SharePoint metadataCustom columns on your library (for example, "Department", "Document Type", "Region")Secondary boost
ActivityRecently accessed or shared documents get a slight boostMinor tiebreaker
People and socialContent from close working network ranks slightly higherMinor tiebreaker

Graph signals only affect ranking of content within the configured knowledge source. They do not pull in content from other SharePoint sites or personal OneDrive.

How Many Results?

CONFIRMED Standard retrieval returns the top 3 text extracts per knowledge source.

CONFIRMED With Tenant Graph Grounding, the system provides a "greater volume of context, with greater precision."

UNCONFIRMED The exact number of extracts with Graph Grounding is not disclosed.

Top 3 means the top 3 text extracts (sections from documents), not the top 3 documents. A single large document can contribute multiple extracts if several sections are relevant.

▼
3

Security Trimming

Before results reach the AI, they are filtered based on the user's permissions:

  • Entra ID delegated authentication (On-Behalf-Of) — the agent acts as the user
  • Only content the user has read access to is returned
  • Permissions are checked live on every query — never cached
  • Microsoft Purview sensitivity labels are enforced (SharePoint connector only)
  • Users without access receive "no results found" with no indication the content exists
▼
4

Summarisation and Response Generation

The AI model receives:

  • The retrieved text extracts (the evidence)
  • The user's original question
  • Conversation history
  • Custom instructions set by the agent maker (tone, formatting, safety rules)

The AI writes a grounded response — it should only use information from the retrieved content, not its general training knowledge. It generates citations linking back to the original SharePoint source documents.

CONFIRMED The model used for generative answers is the latest OpenAI model, hosted on Azure AI Foundry within the Microsoft Services Trust boundary. The model is managed by Microsoft and cannot be changed for generative answers.

▼
5

Safety and Governance Validation

  • Content moderation — blocks harmful, offensive, or non-compliant content
  • Grounding validation — checks the answer is based on retrieved content, catches hallucinated claims
  • Configurable moderation level (Lowest to Highest, default is High)
  • No customer data is used to train any language model
▼
✓

Response Delivered

The user sees the answer with clickable citations linking to the original SharePoint documents.

Chunking — How Documents Are Broken Into Sections

Before retrieval can work, documents need to be divided into smaller searchable sections. A 150-page PDF cannot be stored as one block — it must be broken into pieces so individual sections can be found and matched.

What Is Confirmed

  • Microsoft "dynamically indexes documents and breaks content into meaningful chunks"
  • The system uses "advanced query processing to surface the most relevant information"
  • It uses "the same enterprise-grade retrieval stack that powers Microsoft 365 Copilot"
  • Output is "relevant text extracts" — not full documents

What Is Not Disclosed

DetailStatus
Chunk size (for example, 512 tokens)NOT DISCLOSED
Whether chunking is fixed-size, variable, or semanticNOT DISCLOSED
Whether overlap is used between chunksNOT DISCLOSED
The embedding model used to create vectorsNOT DISCLOSED
How tables and complex layouts are handledNOT DISCLOSED

Why These Details Are Not Published

  • The chunking and indexing pipeline is not owned by Copilot Studio — it is managed by the underlying Microsoft 365 retrieval service
  • Copilot Studio consumes an internal API that returns search results — it does not perform the indexing itself
  • Implementation details may be optimised or changed over time as Microsoft improves the retrieval stack
  • Any specific value published today might not remain accurate in future releases
  • Customers should avoid basing architectural decisions on undocumented internal implementation details
  • The recommended approach is to benchmark actual results using representative questions from your own environment
Important distinction Chunk size (how big each section is) and number of chunks retrieved (how many sections go to the AI) are two different things. The number retrieved is documented (top 3 standard, more with Graph Grounding). The chunk size is not disclosed.

Content Refresh — When Do Changes Appear?

The agent searches a pre-built index, not the actual SharePoint files in real time. The Semantic Index is built in the background before anyone asks a question. At query time, the system searches this already-built index.

Troubleshooting

If the agent cannot find a document:

  1. Check SharePoint search — search for the document using the SharePoint search bar. If SharePoint cannot find it, the agent will not find it either.
  2. Re-index the library — Library Settings → Advanced Settings → "Reindex Document Library" to force a re-crawl.
  3. Check the search setting — the site must have "Allow this site to appear in search results" enabled.

SharePoint vs Azure AI Search — Architectural Trade-Off

The decision is not "which platform has the best chunk size?" It is: which retrieval approach gives the required answer quality, security, operational manageability and level of control?

ConsiderationSharePoint (Managed)Azure AI Search (Custom)
Configuration effortLow — add SharePoint as knowledge source, turn on Graph GroundingHigh — design chunking, choose embedding model, configure search
MaintenanceNone — Microsoft manages indexing, refresh, rankingCustomer responsibility — monitor, tune, re-index
Control over retrievalNone — chunking, ranking, index internals are opaqueFull — chunk size, top-K, scoring profiles, hybrid/vector config
SecurityAutomatic via SharePoint permissionsMust be configured manually
Content freshnessUpdates immediate, new docs ~1 dayDepends on indexing pipeline design
Complex documentsHandled by Microsoft (details undisclosed)Customer controls document processing
Data not in SharePointNot applicableCan index blobs, SQL, APIs, etc.
CostM365 licence + Copilot Credits (if needed)Azure AI Search service + compute + storage
Decision principle SharePoint provides a managed experience with less effort. Azure AI Search provides more control with more responsibility. If the managed approach meets quality requirements, its lower operational overhead is a strong advantage. If custom control is needed, the customer should identify specific requirements that justify the additional engineering work.

Recommended Evaluation Framework

Before committing to a production knowledge source, test with 15 to 20 representative questions covering different scenarios.

Suggested Test Categories

  • Exact lookup (for example, a specific code, reference number, or identifier)
  • Product or category-specific lookup (where the same item differs by variant)
  • Questions requiring information from a table
  • Questions requiring information from multiple sections
  • Questions requiring information from multiple documents
  • Process or procedure retrieval
  • Specification lookup
  • Troubleshooting questions
  • Questions with abbreviations or informal names
  • Questions where two items have similar terminology
  • Questions where the correct answer should be "not found"
  • Questions asked by users with different SharePoint permissions

Evaluation Criteria

CriterionWhat to Assess
CorrectnessIs the information factually accurate?
CompletenessDoes it cover all relevant items and variations?
RelevanceIs the response focused on what was asked?
Citation qualityDo citations point to the right source documents?
DisambiguationDoes it distinguish between similar products correctly?
Unsupported claimsDoes the AI state anything not in the source documents?
ConsistencyDoes the same question produce the same quality answer each time?
Permission behaviourDo different users see only what they should?
Content freshnessAre recent document changes reflected?
LatencyIs response time acceptable?
Decision principle If SharePoint consistently meets quality, security and freshness requirements, its lower operational overhead provides a strong reason to use it. If Azure AI Search is still needed for specific control or custom processing requirements, those requirements should be identified precisely and confirmed to create measurable value. The architecture decision should be evidence-led.
